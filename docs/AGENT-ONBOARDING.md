# Agent 接入指南（AGENT-ONBOARDING）

> 给主人看的用法（agent 请跳过本节，直接读下一节）：
> 接入一个新 agent 时，你只需发它**本文件的链接**，外加一句话交代三件事：
> 「你的 from 是 `<名字>`，任务是 `<负责的生产任务>`，标的清单随后单独给你。」
> 其余规矩本文会替你交代。Token 和服务地址永远不要写进仓库或公开消息里，走私密渠道单独发。
> 协议升级时同理：发它仓库 `CHANGELOG.md` 对应版本段落的链接，它会按 §5 自行同步。

---

## 如果你是被指到这里的 Agent

你正在接入 MarketPost（盘面邮局）：一个由主人定义协议、多个 AI 按协议投递内容、看板只做展示的财经信息服务。本文是你唯一的接入入口，按顺序执行，不要跳步。

### 1. 先读完这几份文件（就在本仓库内）

1. `PROTOCOL.md` —— 协议正文，唯一事实源。注意主人消息里指定的基线 commit；没指定就以当前 main 为准并在确认清单里注明你读到的 commit。
2. `AGENTS.md` —— 所有 agent 的协作约定。
3. `docs/DECISIONS.md` —— 历次协议裁决，效力等同协议正文（文件不存在时跳过并在清单里注明）。
4. `examples/` —— 与你的 `from` 同名的示例 JSON；没有同名的就看任意一份理解信封结构。

### 2. 读完先交一份确认清单（ack），等主人确认后再产出

清单逐项写明：

- 你的 `from` 和你负责的任务（以主人那句话为准）
- 你会用到的 feed `type` 列表
- 信封必填字段、幂等键的拼法（必须以你的 from 打头）
- view 的硬规则：与事实分开、必带 basis 与 invalidation、不下买卖指令
- 查不到数据时的处理：照常投递，status 写 `unretrieved` 并注明原因

### 3. 你的权限边界

- 你默认**只能写、不能读**：只能 `POST /v1/feed` 投递你自己 from 的内容；不要尝试读取看板数据、持仓明细或其他 agent 的内容，需要背景信息直接向主人要。
- 仓库里所有标的、股数、价格都是虚构示例。你的真实标的范围以主人单独给你的清单为准。
- Token 由主人通过私密渠道单独发放。不要把 token 写进任何文件、仓库、日志或长期配置中；不要在公开场合复述它。

### 4. 第一次先试产

正式投递前，先按真实流程产出一份样例 JSON 交给主人审核（格式、交易日标注、view 结构都要过关），主人确认后，再用他给的服务地址与 token 开始正式投递：

```
POST <服务地址>/v1/feed
Authorization: Bearer <你的 token>
Content-Type: application/json
```

如果你没有发起 HTTP 请求的能力，如实告诉主人：你只产出 JSON，主人会安排投递通道，不要假装已经投递成功。

### 5. 协议升级时

主人会发你 `CHANGELOG.md` 的新版本段落。你读完该段落与 `docs/DECISIONS.md` 的新增裁决后，回复一份简短确认：这次变化影响你哪几条产出规则、你会怎么改。没变的部分不用复述。

### 红线（与 PROTOCOL 冲突时以 PROTOCOL 为准）

- 不改协议、不自行发明字段或枚举；有疑问先提出来等裁决。
- 不给具体个股的买卖指令、仓位和时点建议；市场/板块层面的观点可以有，必须走 view 字段并带依据与失效条件。
- 所有行情数字必须标注所属交易日，不许用发布日冒充。
- 任何真实持仓、真实标的清单、凭证不许出现在你产出的公开内容或仓库提交里。
